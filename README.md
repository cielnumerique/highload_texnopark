# Проектирование видеостримингового сервиса

## 1. Тема и целевая аудитория

**Тип:** видеостриминговый сервис на примере Netflix.

**Аудитория:** пользователи по всему миру. Для проекта принимаем 315 млн аккаунтов, MAU = 315 млн и DAU = 189 млн. Ориентир — 301,63 млн платных подписок Netflix в Q4 2024 [1]. Подписки и активные пользователи — разные метрики; MAU и DAU здесь являются допущениями.

**MVP:**

- Регистрация и авторизация.
- Главная страница с рекомендациями.
- Поиск и карточки фильмов и сериалов.
- Просмотр видео с выбором качества.
- «Мой список».
- Оценки.
- Чтение, написание, изменение и удаление отзывов на фильмы.

Рекомендации учитывают историю и оценки. Видео раздаётся через CDN; качество меняется по скорости соединения. Оценки и отзывы доступны после первого запуска видео. На фильм разрешён один отзыв от пользователя; выдача — страницами по 10 записей.

### 2.2. Хранение данных

Размеры записей принимаем по схеме из раздела 5: профиль — 300 Б, список и история — по 24 Б, оценка — 28 Б, отзыв — 1 032 Б.

| Данные | Записей на существующий аккаунт | Объём, КБ |
|---|---:|---:|
| Профиль | 1 | 0,3 |
| «Мой список» | 25 | 0,6 |
| История просмотров | 300 | 7,2 |
| Оценки | 60 | 1,68 |
| Отзывы | 3 | 3,096 |
| **Всего** | **389** | **12,876** |

Для каталога принимаем 10 000 тайтлов: 45% фильмов и 55% сериалов, по 25 эпизодов. Фильм длится 110 минут, эпизод — 48 минут. Получаем 142 000 видеоединиц и 118 250 часов контента.

Все версии качества занимают `0,3 + 1 + 3 + 7 = 11,3 ГБ/час`; мастер-копия — 80 ГБ/час; один постер — до 1 МБ/тайтл. Размеры метаданных — из раздела 5.

| Данные | Количество | Объём, ТБ |
|---|---|---:|
| Видео для раздачи | 142 000 видеоединиц | 1 336,23 |
| Мастер-копии | 142 000 видеоединиц | 9 460 |
| Метаданные, ключи файлов и постеры | 10 000 тайтлов, 142 000 видео, 720 000 файлов | До 0,010457 |
| Профили, история, избранное и оценки | 315 млн аккаунтов | 3,0807 |
| Отзывы | 945 млн записей | 0,97524 |
| **Всего** | | **≈ 10 800,29** |

Объёмы указаны без индексов, журналов и реплик. Итоги рассчитаны до округления; 1 КБ = 10³ байт, 1 ГБ = 10⁹ байт, 1 ТБ = 10¹² байт.

### 2.3. Прирост данных

Новый аккаунт содержит только профиль. Остальные данные появляются при действиях DAU. История создаёт запись при первом запуске видео. Для запаса считаем все просмотры, оценки и отзывы новыми, а операции со списком — добавлениями. Повторы и удаления уменьшают фактический прирост.

| Данные | Новых записей на DAU в сутки, до | Байт на запись | Прирост, ГБ/сутки |
|---|---:|---:|---:|
| История просмотров | 3 | 24 | 13,608 |
| Оценки | 0,3 | 28 | 1,5876 |
| «Мой список» | 0,4 | 24 | 1,8144 |
| Отзывы | 0,01 | 1 032 | 1,95048 |
| **Всего** | **3,71** | | **18,96048** |

Прирост на одного DAU: `3 × 24 + 0,3 × 28 + 0,4 × 24 + 0,01 × 1 032 = 100,32 байта/сутки`.

При линейном росте аудитории на 15,9% средний DAU за год: `189 млн × (1 + 0,159 / 2) = 204 025 500`. Новые профили: `315 млн × 15,9% = 50 085 000`. Их дальнейшая активность уже учтена в DAU.

Годовой прирост пользовательских данных: `(204 025 500 × 100,32 × 365 + 50 085 000 × 300) / 10¹² ≈ 7,49 ТБ`.

Принимаем 600 новых тайтлов в год: 270 фильмов и 330 сериалов. Прирост видео: `270 × 110 / 60 + 330 × 25 × 48 / 60 = 7 095 часов`; число видео — `270 + 330 × 25 = 8 520`, файлов — `8 520 × 5 + 600 = 43 200`.

| Данные | Расчёт | Прирост, ТБ/год |
|---|---|---:|
| Версии для раздачи | 7 095 ч × 11,3 ГБ/ч | 80,17 |
| Мастер-копии | 7 095 ч × 80 ГБ/ч | 567,60 |
| Метаданные, ключи файлов и постеры | `(600 × 4 877 + 8 520 × 28 + 43 200 × (305 + 256) + 600 × 10⁶) / 10¹²` | До 0,000628 |
| Пользовательские данные, включая отзывы | Активность DAU и новые профили | 7,49 |
| **Всего** | До округления строк | **≈ 655,26** |

## 3. Глобальная балансировка нагрузки

### 3.1. Группы трафика

| Условный домен | Трафик | Куда направляется |
|---|---|---|
| `api.stream.example` | Авторизация, каталог, поиск, избранное, оценки и отзывы | Amazon Route 53 (GeoDNS) возвращает адрес регионального AWS ALB; ALB выбирает сервер API |
| `video.stream.example` | Видеофайлы | CloudFront; узел доставки выбирает CDN-провайдер |
| `static.stream.example` | Постеры, JS и CSS | CloudFront; отдельные настройки кеширования для статики |

Домены условные.

### 3.2. Размещение и нагрузка

Используем четыре региона AWS [3]. Доли подписок Netflix принимаем за доли запросов [1]. Для каждого метода: `RPS региона = пиковый RPS метода × доля региона`; резерв — 20% сверх нагрузки при отказе одного региона по разделу 3.3.

| Площадка | Аудитория | Доля | Пик API, RPS | Мощность с резервом, RPS |
|---|---|---:|---:|---:|
| NA — Вирджиния | США и Канада | 29,7% | ≈ 27 696 | ≥ 70 724 |
| EU — Франкфурт | Европа, Ближний Восток, Африка | 33,5% | ≈ 31 240 | ≥ 70 724 |
| SA — Сан-Паулу | Латинская Америка | 17,7% | ≈ 16 506 | ≥ 19 807 |
| AP — Сингапур | Азиатско-Тихоокеанский регион | 19,1% | ≈ 17 811 | ≥ 21 374 |

Вирджиния выбрана как площадка на востоке США [4]; Франкфурт — в континентальной Европе [5]; Сан-Паулу — в Бразилии [6]; Сингапур — в Юго-Восточной Азии.

Для африканской аудитории доступны узлы CloudFront, в том числе в Кейптауне и Йоханнесбурге [7]; API работает во Франкфурте.

### 3.3. Порядок балансировки

Для глобального выбора региона API используем **Amazon Route 53 с географической политикой (GeoDNS)**: задаём направления по географии [8]. Порядок обращения, если готового DNS-ответа нет в кеше:

1. **DNS-запрос** через резолвер пользователя доходит до DNS-провайдера Amazon Route 53. Anycast позволяет обслуживать IP его DNS-сервера из нескольких точек; маршрут выбирается с участием BGP [9]. Это выбор узла DNS.
2. **GeoDNS** возвращает IP регионального балансировщика по географии DNS-запроса. Это выбор региона API.
3. **AWS Application Load Balancer (ALB)** принимает HTTP/HTTPS-запросы клиента и распределяет их между серверами API. В каждом регионе предусмотрен отдельный ALB в нескольких зонах доступности. Инфраструктурой балансировщика управляет AWS; мы настраиваем серверы назначения, правила и проверки доступности [13].
4. **Видео** плеер получает напрямую из CDN по подписанной ссылке от API [10][11].

**Отказ региона:** NA → EU, EU → NA, SA → NA, AP → EU. Из-за DNS-кеша переключение не мгновенное [12].

### 3.4. Доставка через CDN

Для видео и статики используем Amazon CloudFront: готовую сеть доставки с поддержкой подписанных ссылок [10][11]. Четыре выбранных региона относятся к API. Узлы CDN находятся на площадках провайдера по миру и не ограничены этими регионами [7].

Имена видео и статики направлены на CloudFront. При разрешении имени инфраструктура CDN выбирает узел доставки с учётом сетевой задержки [10]. Выбор узла между городами относится к глобальной балансировке; распределение запросов между серверами внутри узла — к локальной. Обоими уровнями CDN управляет провайдер.

API проверяет право на просмотр и выдаёт подписанную ссылку. Плеер обращается непосредственно в CDN. При наличии файла в кеше CDN отдаёт его; иначе получает из исходного хранилища сервиса и кеширует [10].

## 4. Локальная балансировка нагрузки

### 4.1. Балансировка запросов

Используем L7-балансировку, потому что за одним доменом API работают разные сервисы. Реализация — AWS ALB. В каждом регионе два ALB: публичный для клиентов и внутренний для межсервисных запросов. Внутренний доступен только из сети приложения [15]. Соответственно, всего 8 ALB. Далее выбирается экземпляр сервиса с наименьшим числом незавершённых запросов [14].

### 4.2. Отказоустойчивость

ALB и сервисы работают в двух зонах. Каждая рассчитана на всю нагрузку региона с резервом из раздела 3.2, чтобы выдержать отказ другой зоны. ALB проверяет экземпляры HTTP-запросами и исключает неисправные из балансировки [16]. При отказе региона переключаем трафик по разделу 3.3. Межсервисные вызовы ограничиваем тайм-аутами.

### 4.3. Терминация TLS (SSL)

TLS завершается на публичном ALB [17], далее используется HTTP в закрытой сети. Видео и статику обслуживает CloudFront, минуя региональные ALB.

### 5.4. Консистентность и распределение нагрузки

| Данные | Требование | Распределение по ключам |
|---|---|---|
| `users` | Email уникален; подтверждённые изменения аккаунта доступны при следующем входе | Вход — по `email`, профиль — по `user_id` |
| `watchlist`, `ratings`, `reviews` | Пользователь видит своё подтверждённое изменение; повтор запроса не создаёт дубликат | Запись — по паре `user_id, title_id`; у популярных фильмов значительно больше чтений отзывов |
| `watch_history` | Первый запуск сохраняется один раз; проверка права на отзыв видит подтверждённый запуск | По `user_id`; активные пользователи обращаются чаще |
| `titles`, `videos`, `file_metadata` | Карточка публикуется после загрузки файлов; допускаем отставание общей карточки в кеше до 60 с | Основной спрос приходится на популярные `title_id` и `video_id` |
| `file_objects` | По одному ключу доступны одни и те же байты; новая версия получает новый ключ | Премьеры создают повышенную нагрузку на отдельные `object_key` |
| `catalog_cache`, `cdn_cache` | Потеря кеша не приводит к потере исходных данных | Популярные карточки и файлы читаются значительно чаще остальных |
